# 第一版测试条件与结果

验证日期：2026-11-13。Python 3.11.15，macOS，本地 CPU 执行；最终测试与示例均使用 `python -S`，关闭 site-packages 加载，只使用标准库与本仓代码。这是性能模型逻辑验证，没有硬件测量或误差校准。

## 基线与回归

上游基线为 `hmljy2020/ssnpu-model@c5e37d6bad5f622a4ce4046a2b38e86a96240e84`。修改前 45 项测试通过；修改后 **76 项全部通过**，其中新增 31 项 NoC/集成测试（本轮 24 项，另一会话接入的自动规划 7 项）。

三个原 capture 使用同一原始 `default_config()`、不启用通信计划，修改前后分别重放：

| 负载 | 原指令数 | 修改前 / 后总核周期 |
|---|---:|---:|
| matmul | 168 | 7041 / 7041 |
| FA | 320 | 2182 / 2182 |
| ooo | 3 | 22 / 22 |

除总周期外，逐项比较最后完成周期、完整指令时间线及打点、资源统计、存储分配/释放事件、容量峰值/余量和等待统计，结果一致。原有审计继续检查依赖、发射宽度、资源区间、操作数握手、退休顺序和存储生命周期。

## WSE40 集成用例

两组都使用 40 核、5×8 拓扑、每核 PE 0 运行负载；配置仍提供每核 4 PE。每核贡献 256 B，执行 8 路行 AllGather、5 路列 AllGather，再以 `tile.adds` 消费完整结果。320 条模型操作由 80 条 capture 操作和 240 条 Calendar 操作构成。

使用 `config/wse40.json`：核 1.4 GHz、NoC 2 GHz、64 B/flit、12 B 暂定包头、1 周期跳延迟、收发跨域各 2 NoC 周期，固定 512 ns 时隙。Shared 读写各 256 B/核周期、结果延迟 2 核周期。源、行结果、列结果使用不同 Tile 存储槽。

| 输入来源 | 总核周期 | 总时间 | 本核 SRAM 访问 |
|---|---:|---:|---|
| `tile.full` 生成源 Shared Tile | 8140 | 5.814286 µs | 0 |
| 已驻留 SRAM，显式 `tile.load` | 8278 | 5.912857 µs | 每核读 256 B，141 核周期服务 |

两组只替换源数据准备操作，其余数据量、网络计划、消费操作和配置相同。总时间包含准备、通信、消费、退休和消息收尾；不是纯网络传输延迟。第二组的 141 周期为 `ceil((100 ns + 256 B / 1 TB/s) × 1.4 GHz)`；它替换第一组的向量生成成本，因此两组时间差不等于一次 SRAM 服务时间。

每核行阶段远端提交 1792 B，本地补 256 B，目标 2048 B；列阶段远端提交 8192 B，本地补 2048 B，目标 10240 B。全部节点均完成。全片累计 7800 次有向链路 flit 传输、499200 B 线速字节、399360 B 有效载荷字节。每核 Shared 容量峰值 12544 B，Local 峰值 10240 B；端点预约需求峰值为每核 TX 2048 B、RX 8192 B，与 TileReg 容量分别报告。

API 与 CLI 都运行上述负载；文件形式通信计划及输入哈希经过检查。2724 条指令打点可导出原生 Perfetto，Calendar 使用通信阶段标签。网络逐 flit 事件在 JSON 的 `noc.events` 中。

用旧 `tilesim_wse@3445e9942707a54f2ed16323e60260bd07d15c3f` 单独生成参考结果，比较工具仅位于本地验证目录，不是新仓的运行依赖。拓扑、每核 256 B、路由、64 B/flit、12 B 包头、2 GHz 和单跳延迟固定一致。

按每个源包的首个链路事件归一化时间后，**7800 条链路区间逐项一致**：有向链路、flit 序号、相对开始时间、持续时间、有效载荷、包头及填充字节均相同。旧模型的端点是 SRAM，新模型是 SharedTileReg；此对照验证网络迁移，不要求端到端时间等于旧结果 6.094 µs。归一化数据哈希见 `validation/summary.json`。

## 可选自动规划模式

合并用户在“核查 NoC 路由与时隙算法”会话中要求接入的行为级自动规划。`routing: auto` 使用逐树串行的全网窗口，根据包长和路径估算时长；它是另一种软件调度策略，不改变固定时隙基线的参数。

7 项自动规划测试覆盖完整 2×2 组、该组的目的子集、非相邻节点、较大数据包、链路带宽变化、组件执行顺序和非法输入。固定节点 `{0,1,8,9}`、每源 256 B 时，生成 8 棵树、16 次唯一接收写；每核远端收到 768 B。改变包长至 65536 B 或链路宽度至 32 B 时，其余条件保持一致。另运行 40 核自动规划 AllGather，每核 256 B、每核远端提交 9984 B，结果记录在机器可读摘要中。

## 新增测试的控制变量

| 测试 | 条件和检查 |
|---|---|
| 两核链路与端点 | 每源 256 B；检查 10 flits、640 B 线速流量和 SRAM 零计费 |
| 带宽影响 | 仅将链路每周期字节数从 64 改成 32，包头、频率、计划和核参数相同；检查 flit 增加及完成尾部变长 |
| 双时钟 | 仅将核频率改成 2 GHz，NoC 保持 2 GHz；每条链路序列化仍为 0.5 ns |
| 分段发布 | 两核各 256 B；所有本地/远端段写入后才发布，消费者在接收完成依赖之后发射 |
| 源引用 | 将测试源版本明确设为可回收；检查 staging 后可释放，且早于 TX 排空 |
| Shared 预约 | 预约 `[10,11)`，两周期普通写在周期 9 不能启动，独立读允许；普通写在周期 11 可启动 |
| 后台写竞争 | 两核场景额外加入核 0 的 160000 B 普通 Shared 写；检查它等待预约空档，通信照常完成，所有写服务区间不重叠 |
| 重复/陈旧响应 | 同一分段在 pending 和 committed 时重复提交不重复计费；错误范围、旧代际、提前发布、错过预约均报错 |
| SRAM | 读 256 B、写 512 B 使用同一每核串行服务；分别为 141 核周期，总服务 282 周期；Calendar 不计 SRAM |
| 容量 | 两核每核 256 B 源加 512 B 接收目标，将 Shared 容量仅改成 700 B；准入受阻，停滞诊断包含容量原因 |
| 路由与计划 | 拒绝诱导环、断开、非法位对、接收空洞/重叠、源越界和 LocalTileReg 目标；中间只转发节点不落核 |
| 窗口 | 仅将时隙改为 1 NoC 周期；超窗失败，不隐式移动发送 |
| 调用顺序 | 同一计划、配置和 capture，反转全部组件 tick 顺序；完整报告相同 |
| Barrier | capture 原有 barrier 的完成集合加入通信操作，消费者保持正确同步 |
| 真实 PyPTO 输入 | matmul/FA 各取两核末代 Shared 版本的前 256 B，追加一次两核交换；成功导入、传输和计量。保留原合成 memory 路径，不作 DDR→SRAM 硬件映射，用于接口验证 |
| 参数、来源及导出 | 非投机合同、参数 provenance、包头容量、计划哈希和 Perfetto 通信阶段检查 |

完整日志为 `validation/tests-final.txt`，精简机器可读结果为 `validation/summary.json`。原始 capture、完整报告、迁移参考和 Perfetto 文件保存在本地 `workspace/`，不覆盖原仓 `examples/` 归档。
