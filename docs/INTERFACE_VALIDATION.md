## 条件与结果

| 验证 | 固定条件与变化项 | 结果 |
|---|---|---|
| 离线编译边界 | 先编译、JSON 保存再加载；执行时把 route_tree 和 compile_calendar 替换成会抛错的函数 | 广播与真实核回放正常完成，执行中未调用这些函数 |
| 模块边界 | 新 Python 子进程，分别导入真实核／CommUnit | 核不加载 NoC；CommUnit 不加载路由或编译器；标准库依赖检查通过 |
| CalReg 跨轮复用 | 相同配置、布局、流量；第二轮只变 epoch、requestId 和 Tile 版本，并提前提交触发背压 | 两轮成功；相对注入时刻相同，安装配置保持原值 |
| 配置一致性 | 分别只改变版本、平台缓冲容量、opcode、成员或布局；或重复旧 epoch | 明确拒绝；相同 opcode 下安装不同布局在编译时失败 |
| 请求身份 | 各节点使用相同本地 requestId，节点编号不同 | 完成与数据响应正确匹配 |
| 广播／汇集字节 | 节点 0–3；每源 16×16 FP16、512 B；访问 32 B；TX/RX 上限一起取 32 B 或 64 B | 广播三个目标各 512 B 正确；汇集目标逐行拼接 1536 B 正确；峰值不超上限 |
| 二维跨度与 padding | 有效数据仍为 16×32 B；源行跨度改为 40 B，目的行跨度改为 48 B | 全部有效字节正确，目的 padding 保持初值 |
| 资源等待 | 广播输入、配置不变；只让节点 3 的 Prepared 等到核周期 80 | align 晚于资源准备，不提前发数据 |
| 读服务上界 | 相同广播，只把假核读完成延迟增加 1 或 50 核周期 | 加 1 时固定注入时刻不变；加 50 明确报时隙违约并隔离资源 |
| 写失败 | 相同广播，只让节点 3 的写服务失败 | 目标未发布，故障返回 safe_to_release=False |
| 核侧生命周期 | 两核、每源 256 B；源改为可回收，其他条件不变 | 源保持到读取结束之后；消费者依赖本地结果的 wait；分段读取最终只产生一次源读完成打点 |
| 多节点集成 | 40 核、每源 256 B，按行／列构造 gather+broadcast；另测非相邻四节点 | 全部最终消费者完成；中转节点不写入 Tile；容量检查、时间线导出通过 |
| SRAM 本地／远端 | 假 SRAM 128 B、16 B/周期、读写延迟 3 周期；网络 16 B/周期、延迟 2、控制 8 B、头部 4 B、2 项容量 | 本地无网络事件；远端经过请求、SRAM、响应三阶段；落点和读回字节正确 |
| SRAM 写后读 | 假 SRAM 条件不变，在偏移 16 写入 32 B，确认后发读 | 全部 32 B 读回一致；控制和数据方向的字节计费正确 |
| 背压与完成交付 | 网络容量单独减到 1，并将完成消费延迟 20 周期；另把 SRAM 队列改为 1 | 可重试拒绝不丢请求；每笔只服务一次；完成消费前不归还容量 |
| 共享 SRAM 竞争 | 同一目标的本地、远端访问；真实核进一步加入 HBM 搬运，目标 SRAM 降为 16 B/周期 | 三笔各 128 B 共用目标端口，共计 384 B、24 服务周期，无重叠计费 |
| 乱序与并行 | 两个不同 SRAM 的带宽相同；一个读延迟 20 周期，另一个 3 周期 | 服务可并行，响应按 requestId 正确匹配 |
| 网络延迟敏感性 | 同一 32 B 远端读，仅将每方向网络固定延迟从 2 改为 12 周期 | 总时间增加 20 周期，SRAM 服务占用不变 |
| 真实 TLSU 集成 | wse_config，128 B load/store，显式目标核 1；目标核不运行指令 | load 在网络返回后写 Tile，再唤醒消费者；store 在写确认后完成，后继依赖读再发射 |
| 非法与重复输入 | 分别改变目标、范围、载荷长度、身份或回复 | 拒绝／故障；错误写不发布，重复请求不重复服务 |

## 独立示例结果

默认 WSE40 时钟 1.4／2 GHz，访问粒度 32 B、TX/RX 各 64 B。四个假核分别在核周期 0、11、22、33 发起请求。当前保守 Calendar 编译器每个网络时隙发送一段，读／网络／写可重叠。

| 例子 | 排空时核周期 | 缓冲峰值 | 字节检查 |
|---|---:|---|---|
| 0 → 1、2、3 广播 | 406 | TX 64 B；各 RX 64 B | 每个目标 512 B 通过 |
| 0、1、2 → 3 汇集 | 1050 | 各 TX 64 B；RX 64 B | 目标 1536 B 通过 |
| 独立 SRAM 写后读示例 | 35 | 网络在途上限 2 项 | 32 B 通过 |

这些结果验证消息合同、数据位置、时序约束和计量。Calendar 与远端 SRAM 网络当前使用不同的后端资源模型；旧 AllGather 算法和旧 SRAM 启动计费已改变，未据此声称保持旧性能数值或完成 SSM／硬件周期校准。SRAM 访问按一次 Tile 范围聚合，尚未拆成 SSM 默认上限 256 B 的请求。当前反馈队列采用可靠下一拍交付，延迟消费通过占住在途项测试。
